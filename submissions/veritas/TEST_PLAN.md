# Test plan

This file maps the `contracts/` Foundry test suite to the `backed-return-delta-review` rubric clauses, requirement by requirement, and states plainly which clauses are not yet proven. All test names below are verified to exist via `grep -rn "function test_NAME" contracts/test/` at the time of writing. All paths are root-relative, e.g. `contracts/test/Reentrancy.t.sol`.

## 1. How to run

```bash
cd contracts
forge test --offline
```

`--offline` is the reliable invocation in this environment; a plain `forge test` has previously panicked here while building an unrelated system proxy/Etherscan trace component. As of the 8 Aug 2026 additions (per-position insurance claims, staleness registration gate, and a mutation-tested invariant/fuzz suite), `forge test --offline` reports:

```
Ran 15 test suites in 13.12s (45.18s CPU time): 185 tests passed, 0 failed, 0 skipped (185 total tests)
```

The invariant suite is run at `runs=128, depth=64` by default (see `contracts/foundry.toml`'s `[invariant]` section); a `FOUNDRY_PROFILE=deep` variant (`runs=1000, depth=200`) exists for a slower, more exhaustive pre-submission pass via `FOUNDRY_PROFILE=deep forge test --match-path 'test/invariant/*'`.

## 4. Evidence notes on the newest suites

**`contracts/test/Reentrancy.t.sol`.** What makes it rigorous rather than a checklist: every P2 test has a *fully-armed precondition* — a hostile token or hostile pool state genuinely positioned to attempt reentry, not a mock that merely declares intent — paired with a same-block control arm showing the honest path succeeds where the hostile path reverts. The suite also distinguishes *which* defence fired (`AlreadyUnlocked`, `OnlyPoolManager`/`NotPoolManager`, `NothingToClaim`, `CurrencyNotSettled`) instead of accepting any revert as proof, and both currencies of each hostile fixture are separately hostile because the hook hands control to token code at points with different outstanding-delta state depending on which currency's callback fires. `test_P2_DirectAfterSwap_FromTokenCallback_WhileUnlocked_Rejected` goes further: it forges a large fabricated `BalanceDelta` while the manager is genuinely unlocked and shows the hook's 6909 balance still equals exactly its two accounting mappings afterward.

**`contracts/test/PartialFill.t.sol`.** What makes it rigorous: it is the only suite in the repo that sets a binding `sqrtPriceLimitX96` rather than relying on `Deployers`' hardcoded MIN/MAX limits (which always fill 100%), so it is the only suite that can even observe partial-fill behaviour. Each test asserts `sqrtPriceAfter == limit` first, as a precondition check that the fill genuinely was partial, before asserting anything about the fee split. `test_C2_SameRequest_FullVsPartial_DeductionScalesWithRealized` is the strongest single test: it issues the identical swap request against a full-fill pool and a partial-fill pool and shows the absolute deduction differs while the underlying rate stays consistent to a tight tolerance — proving the hook reads `delta`, not `amountSpecified`.

**`contracts/test/InsuranceClaims.t.sol` and `contracts/test/Staleness.t.sol`.** Added alongside the per-position insurance claim mechanism and the pool-registration staleness gate. `InsuranceClaims.t.sol` proves the central JIT-closure claim directly rather than by inference: `test_J1` and `test_J5` (above) are the load-bearing tests, and `test_J9_RemoveNeverReverts_WhenReserveEmptyOrDrsFell` proves the contract's own hard rule ("liquidity removal must never revert") across every edge case reachable from a unit test. `Staleness.t.sol` proves the staleness gate is a registration-time-only property by construction, not merely by omission — `test_S1`/`test_S2` are a positive assertion (identical fee, identical swap outcome) rather than an absence-of-evidence argument.

**`contracts/test/invariant/VeritasInvariants.t.sol` and `contracts/test/FuzzProperties.t.sol` — mutation testing.** Writing an invariant and having it pass proves nothing on its own; a vacuous invariant (or a handler whose actions never reach the interesting state) passes just as easily as a correct one. Four of this suite's invariants were deliberately falsified by editing `contracts/src/VeritasHook.sol` one line at a time, confirmed to fail as predicted, then reverted:

| Mutation | One-line change | Invariant(s) caught by |
|---|---|---|
| M1 | `_afterSwap`: `reserveAmount = totalAmount - progAmount` → `= totalAmount` | `invariant_backingIsExactAcrossPools` — failed on the very first swap in the run |
| M2 | `_claimFor`: removed the `poolReserve` solvency cap (bound (c)) | `test_INV2_Regression_DisburseThenClaim_DoesNotUnderflow` (deterministic) and `invariant_removeLiquidityNeverReverts` (fuzzed, at raised depth) — both failed with `panic: arithmetic underflow (0x11)`, exactly as predicted from the fact that a disbursement debits `poolReserve` without rewinding `reserveIndex` |
| M3 | `unlockCallback`: redirected the Programmable-fee `take()` to `address(this)` instead of the hardcoded recipient | `invariant_programmableFeesReachOnlyTheHardcodedRecipient` and `invariant_hookHoldsNoRawErc20` both failed; `invariant_backingIsExactAcrossPools` stayed green — proof the two custody invariants are not redundant with the backing invariant |
| M4 | `_handleRemoveLiquidity`: `trackedLiquidity -= removed` → `-= removed / 2` | `invariant_trackedLiquidityMatchesPositions` — failed on the first non-trivial removal |
| M5 | `_splitFee`: froze the carried remainder (`nextRemainder = carriedRemainder`), i.e. reverted to per-swap flooring | `invariant_programmableEntitlementIsCumulative` failed (`17207335000000 != 17207335568000`) and all five `ProgrammableFeeCumulative.t.sol` tests failed, including the exact reviewer scenario (`aggregate 10 bps was not collected: 0 != 199`) |

After each mutation the file was reverted and confirmed byte-identical before the next one; the full 160-test suite is green with none of these bugs present. This is the same rigor discipline the project's own README and `PROPOSAL.md` state as the bar for "rigorous": a test that has been shown to fail on the property it claims to protect, not one that merely happens to pass.

## 5. Named gaps

Rows marked ⚠️ or ❌ in §3, restated as concrete next steps:

- **Row 2 (zero-sum, ⚠️).** Closing this means one test that sums every ledger entry — swapper balance, PoolManager reserves, hook's 6909 claims across `programmableFees` and `poolReserve` — across all four quadrants in one assertion block, rather than the two partial checks that exist today.
- **Row 12 (slippage, ❌).** Closing this means a test using a real v4 periphery router with `amountOutMinimum`/`amountInMaximum` semantics, showing the hook's fee is included in the router's slippage check rather than applied invisibly after it.
- **Row 13 (rounding, ⚠️).** Closing this means one test that asserts, as a general property across many DRS/amount combinations, that every `FullMath.mulDiv` truncation in the fee path resolves in the swapper's favour (i.e. the hook never over-collects due to rounding).
- **Row 17 (fork, ❌).** Closing this means a `vm.createSelectFork` test against Unichain Sepolia exercising `registerPool` → `initialize` → `swap` → `claimProgrammableFee` against the real `PoolManager` at its live address.
- **Row 18 (independent review, ❌).** Closing this means an actual third-party audit engagement; nothing in-repo can substitute for it, and mutation testing (§4) is internal rigor, not a substitute for an outside reviewer.

Rows 7, 8, 15, and 16 were closed on 8 Aug 2026 by the per-position insurance claim mechanism's test suite and the new invariant/fuzz suite; row 3 was closed later the same day by the `beforeSwapReturnDelta` (R2) fix, which makes the fee accrue on the quote currency exclusively in every quadrant — see §3 and §4 above for the evidence. This is stated plainly rather than softened: the remaining rows are real, currently-open gaps, not edge cases already covered elsewhere under a different name.
